# N2SF Data Classification Applicability

이 문서는 N2SF, FIPS 199, FedRAMP 20x의 현재 공개 기준을 바탕으로, 데이터 분류체계 아이디어를 이 워크스페이스에 어떤 식으로 적용할 수 있는지 정리한 운영 메모다.

핵심 결론은 단순하다. 이 프로젝트에서는 이 아이디어를 "새 제도"로 밀기보다, `현행 N2SF 3등급을 유지한 채 실무용 오버레이를 덧씌우는 방식`으로 쓰는 편이 가장 안전하고 설득력 있다.

## 공식 기준 요약

### 1. N2SF 1.0

- `국가 망 보안체계(N2SF) 보안 가이드라인 1.0`은 `Prepare -> Categorize -> Identify -> Select -> Assess`의 5단계 적용 절차를 제시한다.
- `C/S/O 등급분류`는 업무정보와 정보시스템에 대해 수행된다.
- 하나의 정보시스템에 복수 등급 업무정보가 같이 존재하면 상위 등급으로 분류하거나 시스템을 분리하는 방향이 제시된다.
- 2026년 3월 26일 KISA는 `2026년 국가 망 보안체계(N2SF) 도입 지원사업` 공고를 게시했고, 수요기관이 `N2SF 적용 대상 식별`, `C/S/O 등급분류`, `적절성 조정`, `운영계획 수립`을 수행하도록 안내했다.

### 2. FIPS 199

- FIPS 199는 정보 유형을 `기밀성(confidentiality)`, `무결성(integrity)`, `가용성(availability)` 기준으로 범주화한다.
- 정보 유형은 각 보안목표별 `LOW`, `MODERATE`, `HIGH`로 표현한다.
- 정보시스템 단위 분류는 해당 시스템에 상주하는 정보 유형들의 `highest values`를 취하는 `high water mark` 방식이다.

### 3. FedRAMP 20x

- FedRAMP 20x는 기존의 정적 문서 중심 인증보다 `automation`, `machine-readable validation`, `continuous monitoring`을 훨씬 강하게 요구하는 방향으로 움직이고 있다.
- 공식 문서도 `machine-readable` 자료를 기반으로 생성되며, 인간이 읽는 문서와 기계가 읽는 패키지를 함께 요구한다.
- 이 흐름은 정책 문서, 문진표, 승인 흔적을 `운영 가능한 데이터`로 만드는 방향과 잘 맞는다.

## 이 프로젝트에서의 해석

아래 내용은 공식 N2SF를 대체하는 제안이 아니라, 이 워크스페이스에서 쓸 수 있는 `운영 오버레이`다.

- `공식 등급`: N2SF 기준인 `C`, `S`, `O`
- `운영 프로필`: 실무에서 승인 난이도와 통제 강도를 더 세밀하게 나누기 위한 내부 보조값

즉, `4등급 체계`는 제도상 새 공식 등급이 아니라 `S를 둘로 나눈 실무 핸들링 프로필`로 설명하는 편이 충돌이 적다.

## 권장 매핑

| 운영 프로필 | 공식 N2SF 매핑 | 쓰는 이유 | 예시 |
| --- | --- | --- | --- |
| `O` | `O` | 공개 또는 외부 서비스 활용이 가능한 정보 | 공개 보도자료, 공개 보고서, 공개 정책문서 |
| `S-Low` | `S` | 내부용이지만 상대적으로 저위험이며 표준 통제로 운영 가능한 정보 | 일반 업무 메모, 비식별 요약, 공개자료 기반 RAG 산출물 |
| `S-High` | `S` | 내부용이지만 상향 검토, 추가 증빙, 승인권자 판단이 필요한 정보 | 사용자 식별자가 포함된 추론 로그, 원문 기반 RAG 인덱스, 내부 감사자료 |
| `C` | `C` | 법령, 임무, 국가안보, 민감 개인정보 등으로 강한 제한이 필요한 정보 | 고위험 개인정보 원본, 비공개 행정자료, 강한 규제 대상 데이터 |

## AI 자산에 대한 적용 예시

이 문서의 실무 가치는 `AI 자산을 분류표 안에 넣을 수 있다`는 데 있다.

| 자산 유형 | 기본 판단 방향 |
| --- | --- |
| 모델 가중치 | 학습 데이터와 재현 가능성에 따라 `S-High` 또는 `C` 검토 |
| RAG 임베딩 | 원문 역추적 가능성과 민감정보 포함 여부에 따라 `S-Low` 또는 `S-High` |
| 추론 로그 | 프롬프트, 사용자 식별자, 응답 원문 포함 여부에 따라 `S-Low` 또는 `S-High` |
| 프롬프트 템플릿 | 공개 가능한 일반 템플릿은 `O`, 내부 운영 템플릿은 `S-Low` |
| 평가 데이터셋 | 개인정보, 내부 정책, 민감 시나리오 포함 시 `S-High` 이상 우선 검토 |

위 표는 추정 규칙이다. 최종 판정은 데이터 내용, 결합 가능성, 기관 책임 구조를 함께 봐야 한다.

## 워크스페이스 적용 포인트

### 1. PolicyRadar

가장 직접적인 적용 대상이다.

- N2SF, CSAP, FIPS 199, FedRAMP 20x, 기계가독형 검증 흐름을 별도 정책 엔티티로 추적
- `국가 망 보안체계`, `C/S/O`, `보안성 검토`, `적절성 조정`, `FedRAMP 20x`, `FIPS 199` 같은 키워드를 정책 리포트에 반영
- 향후 KISA, PIPC, NIST, FedRAMP 쪽 정책 변경을 하나의 레이더에서 묶어 볼 수 있음

이번 변경에서 `policy.yaml`에 해당 추적용 엔티티를 실제로 추가했다.

### 2. GovRadar

정책 내용을 `사업/공고 관점`으로 연결할 때 유용하다.

- N2SF 도입 지원사업 같은 공공조달/지원사업 추적
- 기관별 도입 공고, 실증사업, 컨소시엄 모집, 시범사업 파악
- 실제 수요기관과 공급기업이 어디서 움직이는지 보는 용도

### 3. TrustRadar

분류체계를 `보안 운영 분류`로 내릴 때 핵심 저장소다.

- 침해사고, 유출, 규제집행, 프라이버시 이슈를 `데이터 자산 유형` 기준으로 다시 해석
- `모델 가중치`, `임베딩`, `추론 로그`, `감사 로그`, `학습 데이터` 같은 자산 분류 축을 추가할 수 있음
- 결과적으로 사고 기사 수집을 넘어서 `어떤 유형의 AI 자산이 실제로 사고/제재의 중심인지` 추적 가능

### 4. PaperworkRadar

문진표와 승인 흐름으로 내릴 때 적합하다.

- 문진표 결과를 단순 등급 추천에서 끝내지 않고 `권고 등급`, `상향 사유`, `추가 검토 사유`, `승인권자`, `필요 증빙`까지 출력
- 보안성 검토나 기관 내부 심의 자료로 넘길 수 있는 결과물 형태로 정리
- 향후 `질문 응답 -> 증빙 체크리스트 -> 제출 패키지` 흐름으로 확장 가능

### 5. radar-dashboard

지금 당장 우선순위는 아니지만, 나중에는 다음을 집계 대상으로 올릴 수 있다.

- 저장소별 정책 프레임워크 언급량
- 등급분류 관련 기사 수
- 공공 도입 공고 수
- 자산 유형별 사고/규제 빈도

## 정책 충돌을 줄이는 설명 방식

이 프로젝트에서 가장 안전한 포지셔닝은 아래다.

`현행 N2SF/CSAP를 대체하는 분류체계`가 아니라, `현행 N2SF 3등급을 실무에 적용하기 위한 운영 오버레이와 문진 알고리즘`이라고 설명한다.

이 방식의 장점은 세 가지다.

- 현행 제도와 직접 충돌하지 않는다.
- `왜 4등급이냐`는 질문에 `공식 3등급 + 실무 핸들링 프로필`이라고 답할 수 있다.
- 문진표, 승인흔적, 증빙 요구사항을 설계하기 쉬워진다.

## 문진표 출력 권장 항목

정책 검토 도구로 보이려면 최소한 아래 항목이 필요하다.

- `official_grade`: 공식 N2SF 등급
- `operational_profile`: `O / S-Low / S-High / C`
- `uplift_reason`: 상향 판정 사유
- `review_required`: 추가 검토 필요 여부와 이유
- `approver_role`: 승인권자 또는 검토 조직
- `required_evidence`: 필요 증빙 문서 목록
- `control_hints`: 예상 보안통제나 차단 포인트
- `audit_trace_id`: 나중에 근거를 추적할 수 있는 식별자

## 효과 측정 지표

실증성을 보이려면 아래 네 가지가 우선이다.

- 기존 방식 대비 `상향분류 감소율`
- `분리 가능한 고등급 데이터 비중`
- `예상 인증/검토 범위 축소 효과`
- `분류 검토 시간 단축 효과`

## 이번 점검의 실무 결론

- 이 아이디어는 워크스페이스와 잘 맞는다.
- 다만 `공식 분류체계`로 주장하기보다 `운영 오버레이`로 두는 편이 훨씬 강하다.
- 즉시 구현 가능한 첫 적용 지점은 `PolicyRadar`의 정책 추적 엔티티, `PaperworkRadar`의 문진 출력 확장, `TrustRadar`의 AI 자산 유형 태깅이다.
- 당장 코드 변경 우선순위는 `PolicyRadar -> PaperworkRadar -> TrustRadar` 순서가 적절하다.
